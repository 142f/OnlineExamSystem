### 3.4 关于"第一次对比脚本出现假阳性"（自我纠错记录）

第一次做 JSON 语义对比时，脚本把非 JSON 响应（404/500 纯文本）也当成功解析，
两边都返回 `PARSE_FAIL` 从而判定为"一致"，属于**假阳性**。
第二轮改为打印状态码 + 原始响应体，才暴露出 404→500 的回归。**这条记录保留，作为审查过程的可信度说明。**

## 4. Review #3：修改前后逻辑一致性终审

对比方式：**同一份数据库、同一份请求**，同时打旧服务（9201）与新服务（19201），逐项比对。

### 4.1 正常接口（已登录管理员）

| 接口 | 旧 | 新 | 语义一致性 |
| --- | --- | --- | --- |
| `POST /login` (9991/123456) | 200 | 200 | ✅ 字段与值完全一致 |
| `GET /messages/1/5` | 200 | 200 | ✅ 一致（含 `time` 日期格式） |
| `GET /exams/1/5`、`/exams/3/2` | 200 | 200 | ✅ total=18 / size=2 / pages=9 一致 |
| `GET /teachers/1/3` | 200 | 200 | ✅ 一致 |
| `GET /scores`、`/admins` | 200 | 200 | ✅ `/admins` 逐字节一致 |
| `GET /students/1/3/...`、`/students/2/3/...` | 200 | 200 | ✅ total=6、pages=2、翻页首行 ID 一致 |
| `GET /answers/2/4/_/_/_` | 200 | 200 | ✅ total=36、pages=9、当前页首题 10005 一致 |

**分页结论**：jsqlparser 生效，`PaginationInnerInterceptor` 正确重写分页 SQL，翻页取到不同行，`total/pages` 计算正确。
这是本次升级风险最高的一项，已实测通过。

### 4.2 异常与鉴权语义

| 场景 | 旧（9201） | 新（19201） | 结论 |
| --- | --- | --- | --- |
| 未登录访问受保护接口 | 401 `text/plain;charset=UTF-8`「登录状态已失效，请重新登录」 | 同左 | ✅ 逐字节一致 |
| 不存在的路径（已登录） | 404，空响应体 | 404，「请求的资源不存在」 | ⚠️ 状态码一致，**响应体由空变为中文提示**（改进，非破坏） |

| 请求体 JSON 语法错误 | 500 `SYS Request failed...` | 500 同左 | ✅ 保持一致（沿用旧设计） |
| 请求体为空 | 500 同上 | 500 同上 | ✅ 一致 |
| 密码错误 | 200 + `{"code":400,"message":"请求失败"}` | 同左 | ✅ 一致 |
| 登录体带未知字段 | 200 正常登录 | 200 正常登录 | ✅ 一致（两边都忽略未知字段） |
| 非法 Origin（CORS） | 403 | 403 | ✅ 一致 |
| 合法 Origin 预检 OPTIONS | 200 + `Access-Control-Allow-Origin: http://localhost:9202` | 同左 | ✅ 一致 |

### 4.3 已知且可接受的差异（升级引入，非缺陷）

| 差异 | 说明 | 影响评估 |
| --- | --- | --- |
| **JSON 字段顺序变为字典序** | Jackson 3 默认 `SORT_PROPERTIES_ALPHABETICALLY=true` | 前端按 key 取值，无影响；仅影响肉眼比对与快照测试 |
| **分页对象字段减少** | MP 3.5.18 的 `Page` 不再暴露 `orders/searchCount/optimizeCountSql/countId/maxLimit`，只余 `records/total/size/current/pages` | 前端只用 records/total/pages，无影响；响应体更干净 |

> 这两条正是"语义一致、字节不一致"的来源，已在 4.1 的判定中排除。
